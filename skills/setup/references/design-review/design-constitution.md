# 설계 헌법 (Design Constitution)

유형: 코드 (구조 설계 불변 원칙)

spec의 코드 설계와 구현 전 설계 결정이 지켜야 하는 조항. `/design-review` 판정 기준이며, 조항
위반은 **Blocker** — 채택하려면 사용자 승인 + spec 「의도적 예외」 기록(하단)이 필요하다. 새 사건에서
교훈이 나오면 조항을 추가한다. **조항 번호는 불변, 추가만** (기존 번호 재사용·삭제 금지 —
spec·리뷰가 번호로 참조한다).

## 제1조 — 공유 표면의 도메인 중립

넓게 파생·호출되는 기반 타입·공용 함수·공용 인터페이스는 특정 도메인의 로직/상태를 갖지 않는다.
도메인 기능은 그 도메인을 구현하는 타입 또는 전용 컴포넌트/서브타입에 배치한다.

- 위반 신호: 기반 타입에 특정 도메인 멤버 추가, 범용 함수 안의 도메인 분기

## 제2조 — base-knows-child 금지

부모/공유 타입이 자식(파생·구현체)의 타입이나 구현을 조회하지 않는다 (다운캐스트, 타입 분기,
자기 타입 프로빙). 분기가 필요하면 가상 함수·인터페이스 구현·콜백으로 역전한다.

## 제3조 — 의존 방향

구체는 추상에 의존한다. 모듈 의존은 {DEP_MANIFEST}에 선언된 기존 방향을 따르고 순환을 만들지
않는다. 새 역방향 의존·신규 모듈 의존은 그 자체가 구조적 결정 — spec에 근거를 적고 검토를 받는다.

## 제4조 — 대안 비교 의무

로직/상태의 배치, 새 패턴 도입 같은 구조적 결정은 **대안 2개 이상과 각 기각 사유**를 spec에 적는다.
각 결정은 장점과 함께 대가(비용)를 명시한다. 장점만 서술된 결정은 미검토 결정으로 간주한다.

## 제5조 — 단순성 / 반추상화 (YAGNI)

- 추측성 일반화 금지: 두 번째 사례가 실재하기 전에 일반화하지 않는다. 안 하는 것은 spec
  「비목표(YAGNI)」 절에 명시한다.
- 목적 없는 래핑·중간 레이어 금지: 프레임워크·기존 API를 바로 쓸 수 있으면 감싸지 않는다.

**금지 대상은 추측성 파라미터·확장점이지 이름 붙이기가 아니다.** 소비자가 하나여도 구현에 이름과
자리를 주는 것은 이 조항에 걸리지 않는다. 일반화는 두 번째 사례를 기다리되 **발견 가능성은 미루지
않는다** — 찾을 수 없는 곳에 묻는 것은 단순함이 아니라 은닉이다.

- 오독 신호: 「쓰는 데가 하나뿐이니 호출부에 인라인으로 두자」

## 제6조 — 전역화는 스코프 결정

기능 단위 서비스·서브시스템은 자연스러운 패턴이다. 다만 다음은 구조적 결정으로 spec에 근거(왜
전역 스코프가 필요한가)를 적는다:

- 지역 스코프로 충분한 상태·기능의 전역 승격
- 지나치게 사소한 기능의 서비스화
- 프레임워크 밖 커스텀 싱글톤·정적 매니저 신설

- 위반 신호: 호출 편의를 위한 `get()` 접근점 신설, 단일 소비자뿐인 서비스

## 제7조 — 확장 대신 추출·구성

새 요구사항 때문에 이미 널리 쓰이는 단위를 늘리지 않는다. 공통을 추출하고, 새 사용처는 **자기
단위**가 그것을 조합한다.

- 갈라지는 기준은 **인터페이스 구성**이다. 같은 표면을 값만 바꿔 쓰면 같은 단위 + 인스턴스, 표면
  자체가 달라지면 다른 단위.
- 위반 신호: 기존 단위에 사용처 전용 분기·파라미터·스위치 추가, 옵션 수가 사용처 수보다 빠르게 증가
- 제1조가 「공유 표면에 무엇을 넣지 않는가」라면 이 조항은 「늘릴 것인가 나눌 것인가」를 정한다.
